# Theme lane

One palette, three files, two generators. Nothing in this directory is drawn
by hand.

## What is generated

| File | Generator | What it is |
|---|---|---|
| `wallpaper/meta-wallpaper.png` | `iso/tools/make_wallpaper.py` | 1920x1080 RGBA. Contract black falling to near-black, one blue ring at 30% of the height, soft glow |
| `gtk/metaos.css` | `iso/tools/tokens_to_gtk.py` | `@define-color meta_*` for every token, plus the window, button, entry, menu and selection rules |

Both read `iso/contracts/tokens.json` — the contract vendored from
`opencode1/metaos-1.0`, pinned by sha256 in `iso/contracts/PIN.md`. The
wallpaper takes `black` and `blue`; the stylesheet takes all eight colours.

`xfce4-desktop.xml` is hand-written and is the only file here that is: it is
the Xfce channel that points the desktop backdrop at the installed wallpaper.

## Why generated

The splash, the start page and the desktop must not drift apart. A hand-edited
hex in a stylesheet is a colour that no longer matches the contract, and no one
notices until the screen is up. Generating both from one file makes drift
impossible, and gives the checker something exact to compare against: it asks
each generator `--check` and fails if the committed bytes differ.

## Login screen

The greeter is a GTK surface of its own, so it gets its own files from the
same palette:

| File | What it is |
|---|---|
| `wallpaper/greeter-wallpaper.png` | the ring again, dimmer, smaller and higher, so the name and password fields stay readable |
| `lightdm/lightdm-gtk-greeter.conf` | `background`, `theme-name=MetaOS`, Inter 10, Adwaita icons |
| `lightdm/themes/MetaOS/index.theme` | names the theme directory the config asks for |
| `lightdm/themes/MetaOS/gtk-3.0/gtk.css` | translucent panels, blue buttons, token colours for text and errors |

The first and last are generated by the same two tools as the desktop, so the
splash, the login screen and the desktop cannot disagree about a colour.

**Status: CODE-INSPECTED.** No greeter has been started. Whether LightDM
picks up a `theme-name` that Xubuntu did not ship is exactly what a login run
on the 32GB machine settles.

## Boot menu

GRUB draws its own screen before any of this exists, so it gets a third
variant of the ring and a theme file:

| File | What it is |
|---|---|
| `boot/grub/themes/metaos/meta-grub.png` | the ring small and high, field at about a third brightness, lower two thirds left quiet for the menu |
| `boot/grub/themes/metaos/theme.txt` | generated: image name, title, and one `+ boot_menu` block with geometry and two contract colours |
| `boot/grub/metaos-theme.cfg` | drop-in for `/etc/default/grub.d/`, setting `GRUB_THEME` and showing the menu |

No font is named in `theme.txt`. GRUB resolves fonts by the names in loaded
`.pf2` files; a name with no file behind it would render nothing, and
`grub-mkfont` is not run here. GRUB's own font applies.

The drop-in deliberately sets no `GRUB_CMDLINE_LINUX` or
`GRUB_CMDLINE_LINUX_DEFAULT`: the kernel command line belongs to the base
image or to whoever runs the install. The checker fails if this file ever
grows one.

**Status: CODE-INSPECTED.** No GRUB has read this theme, and nothing here has
run `update-grub`.

## Regenerate

```
python3 iso/tools/make_wallpaper.py
python3 iso/tools/tokens_to_gtk.py
```

## Where it lands

`iso/tools/apply.sh` installs the wallpaper and the stylesheet to
`/usr/share/metaos/theme/`, and the channel to
`/etc/xdg/xfce4/xfconf/xfce-perchannel-xml/xfce4-desktop.xml`.

Two honest limits:

- Xfce keys the backdrop by monitor name. The shipped channel uses
  `monitor0`/`workspace0`; on hardware with a different name Xfce creates its
  own key on first login and the default may not apply. Seeing this work needs
  a screen.
- Activation is `iso/base/meta-first-login.sh`, not `apply.sh`: the wallpaper
  is written to every backdrop property the session reports, and the
  stylesheet is copied to `$HOME/.config/gtk-3.0/gtk.css` for that account.

**Status: CODE-INSPECTED.** The PNG header is decoded and its dimensions and
colour type are checked; the pixels have never been seen on a display.

## Desktop shell

The greeter hands the session to `xfce4-panel`, and until now nothing
configured it. Five surfaces, all generated by `iso/tools/tokens_to_xfce.py`:

| File | What it is |
|---|---|
| `xfce4/xfconf/xfce-perchannel-xml/xfce4-panel.xml` | one top bar: whisker menu, four launchers, task list, tray, clock, show-desktop. Backdrop is the contract black at 92% |
| `xfce4/.../xsettings.xml` | theme `MetaOS`, icon theme `MetaOS`, Inter 10, antialiasing on |
| `xfce4/.../xfce4-power-manager.xml` | blank at 10 min, lock on suspend |
| `xfce4/.../light-locker.xml` | lock on suspend and after the screensaver |
| `icons/MetaOS/` | `index.theme` inheriting Papirus-Dark then Adwaita, plus three original place icons |
| `fonts/local.conf` | Inter first, DejaVu Sans behind it, monospace DejaVu |
| `apps/terminal/metaos.theme` + `terminalrc` | 16-colour palette; the bright half is computed from the dark half |

The panel names four `.desktop` files by name. The checker fails if one of
them is missing, because a launcher pointing at nothing is a dead icon.

system-wide `xfce4-panel.xml` before the first login, and whether the whisker
