# Limits, and the test that tries to break each one (BF4-17)

Generated by `os-build/layer1/gen_limits.py`. Every numeric limit constant in
`services/` is listed. **75 of 95 are exercised by a test**, 20 more carry a named
reason why no driver can settle them, and **0 are still open**.

Two ways a limit counts as proven: the test names the constant, or the test
breaks the limit through the public API and the override table says which check
does it. Nothing is marked proven because it "looks covered".

The converse is not true: a limit can be exercised by a test that never names
it, and it will still read UNPROVEN here. Treat the top table as a lower bound
on coverage and the bottom one as the list to check by hand.

## Named reason — no driver can settle these

Each row is a claim about why a test cannot exist, which is a different thing
from coverage. **DEAD** rows are findings: the limit in the name is enforced
nowhere in the source, so the constant is a comment pretending to be a check.

The DEAD rows in that table are not 'unproven', they are **not limits**: ``EX_NAME_MAX`, `DL_LIT_MAX`, `FS_MAX_DEPTH`, `CK_MAX_BLOCKS`, `CK_MAX_INODES``. Nothing enforces them, so nothing can refuse at their edge. The fix is to
enforce the bound where the name promises one, or delete the constant. Both are
outside this lane's frozen surface, so they are reported, not patched.

## Why this document exists

A quota test is the only kind of test that fails in a way nobody notices: the
code works at every size below the limit, so ordinary use passes, and the
failure only appears on the day the data is big enough — which is the day it
matters. Enumerating the limits is the cheap half; the table above is the half
that says which ones are still guesses.
