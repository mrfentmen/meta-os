Generated by `os-build/layer1/boot_rehearsal.sh`. The order is read from
`services/supervisor/bootorder.goose` (`BO_NAMES`), and each line below is the
program's own stdout, captured to `os-build/layer1/host/build/rehearsal/<svc>.log`.
Regenerate with:

```
./os-build/layer1/run_native.sh          # builds the entry binaries
./os-build/layer1/boot_rehearsal.sh 5    # 5s wall clock per service
```

**What this is.** 25 services have no entry point at all, so they cannot be started
by anything; the rest were started here, one host process each, in the supervisor's
order. That is a rehearsal of the *order and the entry points*, in a host runtime, and
it is the closest thing to a boot this layer has.

**What this is not.** No kernel started these. There is no address space, no privilege
boundary, no scheduler, and no concurrency: service 2 runs after service 1 exits. A
service that hangs is killed by this script's timeout, not by the supervisor — because
the start timeout the layer promises does not exist (`FAILURE_TRACE.md` item 4).

## What the rehearsal found

1. **`console` hangs.** It prints its banner, then loops on `sys_read_key`; the host
   shim answers "nothing pending", which is a valid answer, so the loop never ends.
   This is the start-timeout failure class, demonstrated rather than described:
   nothing in this layer can notice it.
2. **`time` starts and says nothing.** Exit 0, zero lines — the entry has no status
   line. A service that cannot be seen starting is not proven to have started, which
   is why the supervisor's proof line (BOOT_PLAN S7) is specified as a printed line.
3. **`bootlog` and `logd` both start cleanly** and print their state, in order, with
   the fields the boot record expects.
4. **25 of 29 services cannot start at all** — no `entry.goose`. Those are the
   real load-plan blockers, named by service in the table above.
