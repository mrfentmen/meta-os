## The three I would load first, and why exactly these

**1. `bootlog`.** It is the only service whose job is to prove another service started, so every
later stage's proof line is its output. Order 1 with no dependencies, and it needs one syscall that
already exists (`sys_write_serial`, number 1). Nothing else can be debugged until this works.

**2. `storage`.** Order 4, needs nothing from the kernel, and it is the substrate for the rollback
record, the filesystem and log retention. It is also the cheapest second win: `sys_*` calls are zero,
so if it fails, the failure is in the loader, not in a syscall.

**3. `time`.** Order 3, and it is the first service that cannot start honestly without `sys_ticks`.
Loading it third forces the one ABI decision the whole layer is waiting on, at a point where only
two services are at risk instead of twenty-two. If `sys_ticks` is refused, `time` degrades to a
monotonic counter from boot and the rest of the table is unaffected — that fallback is worth ruling
on the same day.

Why not `supervisor` third: it is order 6 for a reason (`bootorder_check.py` proves it), and it
cannot start a child until P3 exists. Loading it before anything it can start proves only that a
binary jumps to an entry point.

## Wire or delete: the whole service list, by class

**Wire (17 services, zero kernel calls beyond the five in the freeze).** These are decided work:
`devices`, `storage`, `callmatrix`, `supervisor` (decide-only), `logfmt`, `fs`, `input`, `netcfg`,
`socket`, `session`, `watchdog`, `audit`, `dhcp`, `dns`, `timesync`, `updater`, `agenthost`.
They need a loader, not a ruling. `BOOT_PLAN.md` S1–S4 is the loader.

**Wire, but only after one ruling each (8 services).**

| Service | Blocked on | Proposal | If refused |
|---|---|---|---|
| `bootlog`, `logd`, `time`, `console`, `display`, `shell`, `example` (7) | `sys_ticks` (P1) | P1: `sys_ticks() -> u64` monotonic ms since boot | keep a boot-relative counter in each service; timestamps lose wall-clock meaning |
| `net` (1) | `sys_net_send`/`sys_net_recv` (P2) | P2: two calls, length-prefixed frames | keep the in-memory link; the network stays a test harness |
| `supervisor` — starts without P3, cannot act without it | `sys_spawn`/`sys_kill` (P3) | P3: `sys_spawn(image, entry) -> pid`, `sys_kill(pid)` | the supervisor stays a decision engine with no actor — today's state |

**Delete candidates (4 directories, no code).** `sockets`, `registry`, `devmgr`, `build`. Each is a
README or an empty directory. The honest options are: delete them from the layer's count, or write
them. `PROPOSALS.md` costs the first three; `build` has no spec at all and should be deleted unless
the boss has one in mind.

**Hold, do not wire (0).** Nothing in the corpus is waiting on a decision that is not listed above.

## What this page is not

- It is not a build plan. `BOOT_PLAN.md` has the stages, the preconditions and the exact proof lines.
- It is not a promise that any of them starts. **No service has ever been started by this kernel**;
  the 29 green runs are host processes against a substituted syscall surface.
- It is not a proposal to allocate syscall numbers. The freeze holds; `PROPOSALS.md` asks.
