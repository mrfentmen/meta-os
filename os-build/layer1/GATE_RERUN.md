## Did any ABI class change because of `read_key`?

**No, and the reason matters.** `read_key` is syscall **5**, inside the F1 freeze (0 exit, 1 write,
2 sleep, 3 pid, 4 yield, 5 `read_key`, 6–15 reserved). It was already in the frozen table before the
kernel implemented it, so a service that calls it was never "needs a proposal" and does not become
one now. What changed is only whether the call can return anything on metal.

Checked against the generated manifest (`services.json`, produced by `gen_services.py` from the
imports, not from memory):

| Class | Count | Services |
|---|---|---|
| Library, no kernel calls | 17 | agenthost, audit, callmatrix, devices, dhcp, dns, fs, input, logfmt, netcfg, session, socket, storage, supervisor, timesync, updater, watchdog |
| Needs a proposal | 8 | bootlog, console, display, example, logd, net, shell, time |

The proposal class is unchanged at 8, and the calls that put them there are `sys_ticks` (P1) for
seven and `sys_net_send`/`sys_net_recv` (P2) for `net`. `sys_read_key` contributes to no service's
class. `sys_write_serial` (1), `sys_write_console` (1), `sys_yield` (4) and `sys_exit` (0) are the
rest of what the class-1 services call, all frozen.

`SERVICES_SYSCALL_MAP.md` was regenerated by `gen_services.py` in this pass, so the map and the
manifest agree by construction.

## What the re-run does not say

- **Nothing ran on the kernel.** All 33 programs are host processes against `host_shim.c`, which
  still refuses `sys_read_key` with "nothing pending" — that refusal is why `console` hangs in
  `BOOT_REHEARSAL.md`.
- **The gate is still per-program.** Goose resolves imports from the root file, so 39 programs is
  39 roots + test roots, not 39 services.
- **`read_key` landing does not move the run count on its own.** It moves what a *kernel* shell can
  do; the services shell was already using `sh_exec`, which takes a line.
