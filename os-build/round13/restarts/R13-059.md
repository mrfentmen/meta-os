# R13-059 — fs restart / state survival

Status: **GAP FILED — volatile RAM disk, no kill harness**.

## Requested condition

Kill `services/fs` mid-work, restart it, and record exactly what state survived, what
was lost, and what it re-did. Proof requires before/after state hashes plus a restart log.

## Evidence

`services/fs/README.md` “Persistence: none, and it says so” states the backend is storage's RAM disk and a restart does not keep files. `DESIGN.md:138-159` says the crash story is theoretical; there is no journal or durable image.

## State ledger

| Question | Answer |
|---|---|
| Survived | Within one process, a remount preserves the files (existing tests). Across a process restart, nothing survives. |
| Lost | Superblock, allocation bitmap, inodes, directory entries and every file block, because the block device is RAM. |
| Re-did | A restarted process must format/mount from scratch; files created before the kill are gone. No multi-block update is replayed because no durable log exists. |

## Gap

A real kill-mid-write hash needs a durable block backend and a fault injector. Without them, any hash would be of process memory, not a recovered filesystem.

## Owner

fs crash consistency; B-L1-74 durable block driver.
