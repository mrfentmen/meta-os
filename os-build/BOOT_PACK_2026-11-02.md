## The run: check in this order, tick off against the log

1. Banner. On VGA and serial, in order (from `kernel/src/main.rs`
   on main):
   - `META OS 0.1 (K6)`
   - `META OS KERNEL - alive (K1)`
   Both lines, or the run has not started. Keep the full serial
   transcript — it is the proof artifact.
2. Shell. The console is no-prompt by design (Pax ruling). Type:
   - `status` — shape `tasks N ticks N heap_free NK`.
   - `help` — exactly `commands: status help uptime mem ps`.
     `clear` and `fetch` stay UNLISTED (ruled, same as clear).
   - `uptime`, `mem`, `ps` — each prints its real line; no
     invented numbers anywhere.
3. `clear` (RW4-2, on main). Blanks the VGA screen, cursor parks
   at 0,0. The serial transcript is untouched — clear touches
   only the VGA buffer. If the serial log blanks, that is a bug,
   not a pass.
4. `fetch` (W6 — check ONLY once the W6 merge has landed).
   Logo frame 0, then, in order:
   - `Mrfentmen@metaos`
   - `OS: Meta OS 0.1 (K6) x86_64`
   - `Host: bare-metal Rust kernel (no_std)`
   - `Kernel: META OS KERNEL - alive (K1)`
   - `Uptime: Ns ticks N`
   - `Tasks: N`
   - `Mem: frames_free N frames_total N heap_free NK heap_total NK`
   - `Programs: hello sleeper crasher (ring 3)`
   Every number comes from the same getters `status`/`mem`/
   `uptime`/`ps` use. The shell resumes exactly where it was.
5. Readkey (check ONLY once the readkey merge has landed):
   userspace `readkey` bin over syscall 5 `read_key`. Do not
   mistake the pre-merge state for a failure: on parent main the
   readkey bin failure is pre-existing because `sys_read_key`
   is unmerged (noted in Milo's W6 gate log).
