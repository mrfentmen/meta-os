## Port rules (binding — from the rust-port skill)

- **Port behavior, do not redesign.** The source is the specification: same inputs, outputs, edge cases, error shapes. If the original does something odd, port the oddity and note it.
- **Tests first** where tests exist; then the code. Parity is case-by-case, not 'similar coverage'.
- **Python/Node originals stay untouched** and remain the live fallback until this batch is PORTED.
- **Shared types live in the owning crate** — depend on them, never copy-paste types between crates.
- **Use the `rustdocs` MCP tools** for crate APIs instead of guessing them.
- Small commits, push often; read the live tip before every push; **never force-push**.

## Done criteria

- Compiles at gate 1 (Milo's VM in topology A; the local Mac in topology B) **and** gate 2 (the boss's Mac). Nothing counts as compiled from the Pax sandbox.
- Every parity case above passes; exclusion-blocked cases are named in the completion report.
- The Python/Node originals are untouched.
- Commit message format: `B23: <piece> — UNCOMPILED` while unproven; `B23: <piece> PORTED` only after both gates + parity pass.
- Completion report (one line): `B23 <PORTED|CARRIED|BLOCKED> crate=os-boot gate1=<pass/fail/na> gate2=<pass/fail/na> parity=<passed>/<total> excl-blocked=<n> commit=<sha>`

## Known traps

- Most of this batch is shell scripts, systemd units, and image-build config: carry them unchanged as deployment assets. The ported code is the `os/mos/` CLI side and the behavior the `test_mos_*.py` cases pin down. Units named `relay-*` here are in-tree OS assets (not the excluded muse-relay repo files) and are in scope.
